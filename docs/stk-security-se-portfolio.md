# 보안 솔루션 SE 지원 포트폴리오 | 고객 환경 이해 · 기술 검증 · 기록

> **STK 보안 솔루션 엔지니어(SE) 지원용으로 재구성한 교육 프로젝트 기록**  
> 실제 기업 고객사 도입 프로젝트 또는 STK 취급 제품의 직접 구축 경험이 아닙니다.

**핵심 요약:** 사용자·단말 요구조건에 맞춰 네트워크를 설계하고, 설정값과 실제 동작을 구분해 검증했습니다. 별도 웹 보안 과제에서는 인증·소유권 기반 접근제어와 비인가 요청 차단 결과를 점검했습니다. 보안 솔루션 도입 전 고객 환경과 요구사항을 확인하고, 테스트 결과를 근거로 설명하는 SE 업무에 연결하고자 합니다.

## 2. 사례 A — 요구조건을 네트워크 구성과 검증 항목으로 연결

**문제와 조건.** 부서와 층별 단말 수가 다른 가상의 백화점 강남점에 동일한 망을 부여할 수 없었습니다. 교육용 사용자 주소 블록 `10.10.8.0/22`를 구역별로 나누고, 부서 간 라우팅 및 공통 서비스 접근을 설정해야 했습니다.

**본인 담당.** 강남점의 VLAN·VLSM 주소 계획, GNS3/Cisco IOS 장비 설정, 테스트 및 DHCP 관련 오류 점검. 본사·다른 지점·데이터센터의 전체 구현을 혼자 맡은 것은 아닙니다.

| 대표 구역 | VLAN | 네트워크 | 게이트웨이 |
|---|---:|---|---|
| 매장 운영 | 10 | `10.10.8.0/25` | `10.10.8.1` |
| VIP/고객 서비스 | 30 | `10.10.9.0/26` | `10.10.9.1` |
| POS | 120 | `10.10.11.192/26` | `10.10.11.193` |

**확인 과정.**
1. GNS3에서 Access–Distribution–Core 구조를 구성하고 VLAN, SVI, 라우팅, DHCP Relay를 설정했습니다.
2. 자기 VLAN의 게이트웨이 Ping 성공과 다른 VLAN의 통신을 구분하여 점검했습니다.
3. DHCP 서버까지의 Ping이 성공해도 클라이언트에 주소가 할당되지 않았습니다. 라우팅 → `ip helper-address` → 서버 서비스/실습 IOS 설정을 순서대로 확인했습니다.
4. 강사님의 자문으로 실습 IOS 환경에서 `service dhcp` 설정 필요성을 확인해 적용했습니다.
5. 이후 **2026.10.19 VLAN 30 테스트 PC의 DHCP 주소 `10.10.9.10/26`, 게이트웨이 `10.10.9.1`, 서버 `10.10.20.10`을 실제 화면으로 재확인**했습니다.

**근거 자료:** [강남점 토폴로지](../gangnam-topology.png) · [OSPF 경로 캡처](../ospf-routing.png) · [VLAN 30 DHCP 임대 캡처](../evidence/dhcp-vlan30-2026-10-19.png) · [트러블슈팅 상세](troubleshooting.md)

**검증의 한계:** VLAN 30의 DHCP 임대는 재확인했지만 전 VLAN·전 사이트의 최신 동작을 다시 검증했다고 주장하지 않습니다. OSPF 자료는 실습 당시 캡처입니다.

## 3. 사례 B — 로그인과 접근권한은 실제 요청으로 확인

별도 [BYTE BACK 프로젝트](https://github.com/hongbin9305/choi-bujang-secret-vault)는 GitHub·Vercel·Supabase를 사용한 단계별 웹 보안 과제입니다.

- **확인 질문:** 비로그인 사용자, 자신의 자료를 요청하는 사용자, 다른 사용자의 자료를 요청하는 사용자, 관리자 API에 접근하는 일반 사용자의 결과가 구분되는가?
- **실습 항목:** Supabase Auth를 통한 로그인, 자료 소유권 기반 조회 제한, API 접근 통제, 접근 이벤트 기록·조회.
- **README에 기록된 결과:** 비로그인 자료 요청 **401**, 일반 사용자 관리자 API 접근 **403**, 소유자별 자료 격리 확인. 이후 단계에서는 타인 자료의 조회·수정·삭제 차단 및 감사·탐지 규칙을 다뤘습니다.
- **AI 활용 범위:** AI의 도움을 받아 원인·수정 방법을 탐색하고, 제안된 변경을 적용한 다음 테스트·채점 피드백으로 확인했습니다. 독자적인 기업 보안 아키텍처 설계·상용 구축 실적은 아닙니다.

**근거:** [BYTE BACK 저장소와 단계별 검증·한계](https://github.com/hongbin9305/choi-bujang-secret-vault). README에는 특정 단계의 미실행 테스트도 명시돼 있습니다. 이 문서의 테스트 표는 해당 저장소의 기록을 요약한 것이며 현재 운영 배포에서 새로 실행한 실측 결과가 아닙니다.

## 4. 보안 솔루션 SE 업무와의 연결

| SE 업무 | 프로젝트에서 익힌 접근 | 실무에서 우선 배울 점 |
|---|---|---|
| 고객 환경·요구조건 파악 | 단말 수·망 구분·주소 블록을 확인하고 구성안에 반영 | 고객 시스템 구조와 도입 제한사항 확인 |
| PoC/BMT 지원 | 명령/설정이 아닌 결과를 기준으로 확인 | 제품별 테스트 항목·합격 기준·증적 기록 |
| 기술 문의·장애 대응 | Ping 성공과 DHCP 서비스 성공을 구분, 구간별로 진단 | 고객 장애 재현·원인 분리·벤더 협업 |
| 고객·파트너 설명 | 인수인계 문서 작성, 교사·거래처 대응 경험 | 기술적 사실과 미확인 사항을 구분한 설명 |

**지원자의 업무 태도:** 고객 환경을 먼저 듣고, 어떤 조건에서 어떤 결과를 확인했는지 남기겠습니다. 재현하지 못한 결과를 성공이라고 쓰지 않고, 교육 환경의 경험과 고객사의 실무 경험을 구분하겠습니다.

## 5. 검증 범위·참고

- 교육 과정과 팀 실습의 산출물을 토대로 구성했습니다. 교육용 테스트를 실제 고객사 PoC로 표현하지 않습니다.
- 프로젝트 도중 강사와 AI의 도움을 받은 부분은 구분했습니다.
- 이 포트폴리오는 STK/SCK의 공식 자료가 아니며, STK 판매 제품(Proofpoint, SailPoint, Ivanti 등)을 직접 운영한 경험을 주장하지 않습니다.
